# Installation and repeatable verification

The web runtime is Apache + PHP 8.x with PDO MySQL + MariaDB 10.4 or newer. No Node, Python, Composer, API keys or internet connection is needed after installing the server and importing SQL. Development tools are optional.

## XAMPP / evaluation server

1. Start XAMPP Apache and MariaDB. Keep existing applications and accounts intact; choose another port if occupied.
2. Copy **the contents of `team05/` into `htdocs/team05/`**. The entry is `http://localhost/team05/`. Keep SQL/data/tests outside the document root.
3. Use the assigned database **team05**, user **team05**, password **team05**. `team05/config.php` contains these public evaluation defaults: host 127.0.0.1, port 3306, utf8mb4. If the environment differs, copy `config.local.example.php` to `config.local.php` and adjust the central array; do not commit that file.
4. Check both CLI `php -m` and the Apache PHP environment for pdo_mysql. PHP 8.0 is the syntax compatibility target (the nonreturning handler uses void plus exit). Actual runtime validation uses PHP 8.2.12 and 8.2.35; PHP 8.0 runtime, professor-server OS/version and Windows/macOS remain untested. No mbstring dependency is required for Unicode character validation.
5. Connect from a database client, for example:

```bash
mysql --host=127.0.0.1 --port=3306 --user=team05 --password --default-character-set=utf8mb4 team05
```

6. Inside the client, replace the path with your actual extraction location, then run:

```sql
SOURCE C:/PATH/BigData/sql/dbcreate.sql;
SOURCE C:/PATH/BigData/sql/dbinsert.sql;
SHOW TABLES;
SELECT COUNT(*) FROM daily_temperatures;
SELECT location_id,COUNT(*),MIN(weather_date),MAX(weather_date)
FROM daily_temperatures GROUP BY location_id;
```

On Linux/macOS use an actual absolute path such as `/path/to/BigData/sql/dbcreate.sql`. The count is 5,480 weather records, 1,096 per location. There are six tables and 5,569 reference/data rows in total. Saved plans initially have zero records.

7. Open Home, the four separate analysis menus, Seasonal Information, and Saved Plans. Create a plan, edit locations, apply it to an analysis and delete it.

Only when you own a **new local** server and no allocated DB/account exists, an authorized administrator may prepare it:

```sql
CREATE DATABASE IF NOT EXISTS team05 CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER IF NOT EXISTS 'team05'@'localhost' IDENTIFIED BY 'team05';
GRANT ALL PRIVILEGES ON team05.* TO 'team05'@'localhost';
```

This does not change an existing account password. Host account matching can differ; use your actual administrator setup. Administrative SQL is deliberately absent from the four required project SQL files. The application never connects as root.

## Reset and restore

`dbdrop.sql` deletes all six project tables, including saved plans. Back up first. On an explicitly disposable/new evaluation database:

```sql
SOURCE /absolute/path/sql/dbdrop.sql;
SOURCE /absolute/path/sql/dbcreate.sql;
SOURCE /absolute/path/sql/dbinsert.sql;
```

To test a dump independently, start with zero project tables and import **only** the dump, with team05 selected:

```sql
SOURCE /absolute/path/sql/dbdrop.sql;
SOURCE /absolute/path/sql/dbdump.sql;
```

`dbdump.sql` was generated by actual MariaDB 10.4 mysqldump; it contains structure, indexes, constraints and all reference records, with empty saved plans. It contains no server users or private credentials. A newer MariaDB dump client may add an incompatible sandbox-mode header; use a client known to work with the evaluation server and retest its output.

Changing the database name requires changing `USE team05` in create/insert/drop as well as the PHP configuration. The supplied dump is imported into the DB selected by your client. Avoid blindly overwriting an existing database.

## Optional isolated Docker development

From the repository root:

```bash
./tools/dev.sh up
./tools/dev.sh init
```

The initialization command refuses an existing schema. Visit `http://127.0.0.1:8055/team05/`. `./tools/dev.sh down` stops only this Compose project and preserves its volume. Do not use `down -v` unless you intend to erase its data.

`./tools/dev.sh lint` checks PHP syntax. `python3 tools/verify_install.py` creates a uniquely named fresh MariaDB volume and internal-only network, copies source to a different path and runs all database calculations, transactions, HTTP flows, reset and dump-only restoration. It removes only its own temporary containers/volume/network. The primary DB is preserved. A local image build is required first; the verification runtime itself has no public network access.

Other developer checks:

```bash
python3 tools/validate_data.py
python3 tests/oracle.py
python3 tests/common_http.py
python3 tests/plans_http.py
node tests/browser.mjs
```

The browser script requires a developer-local Playwright install at `.local/browser/node_modules/playwright` and browser binaries in `.local/ms-playwright` (or explicit `SLG_PLAYWRIGHT_PATH` and `PLAYWRIGHT_BROWSERS_PATH`). These are excluded from the delivered runtime. Never run test suites against a real shared database containing important user plans. The install-verification script confines destructive checks to its fresh DB.

## Reproduce the optional official XAMPP compatibility test

`./tools/prepare_xampp.sh` downloads the pinned official Linux 8.2.12 installer and installs it only inside a new Docker container. No host package/configuration is modified. The vendor installer creates thousands of manual-page symbolic links and can take several minutes; do not mistake its silent period for an application test result.

Then run `python3 tools/verify_xampp.py`. It copies only delivered PHP into the real `/opt/lampp/htdocs/team05` path, provisions a new disposable DB/account, uses unchanged evaluation config defaults, disables all container networking and verifies every analysis, HTTP CRUD, rollback, reset and dump-only restore. Actual observed result: PASS. The precise PHP/Apache/MariaDB versions and SAPI checks are retained in evidence/xampp-install.json.

## Revision evidence and optional document tools

The revision's complete current matrix is generated from `docs/evidence/revision-2026-11-12/`, preserving the original evidence as historical records. For selected checks, `python3 tools/record_results.py --fail-on-error --ids T01 T02 T04` returns nonzero if evidence is absent, failed, incomplete or stale. Running the matrix generator does not execute the tests. Each JSON retains actual execution time, command, environment and tested input hashes.

The application used for final captures is source commit e12ee89cd59964d2e58e601a7acfcd537dcecce8, deployed from a committed ZIP to a separate Apache document root. Later package/document commits preserve the same application manifest. Actual serving-container hashes and HTTP asset checks are separate from working-tree/package checks. See deployment-media.json and the final ZIP's COMMIT_SHA.txt, RELEASE_MANIFEST.json and VERIFICATION.json. Whole-ZIP SHA-256 sidecars stay outside the archive.

Optional developer document dependencies are listed in tools/qa-package.json and tools/qa-requirements.txt. `tools/render_documents.mjs` renders PDFs with real page counts. `tools/update_report.py` extracts exact current code with source/line/hash references. To prepare the optional presentation renderer when internet is available:

```bash
docker build -f tools/document-render.Dockerfile -t seasonal-team05-document-render:2026-11-12 .
python3 tools/make_slides.py
python3 tools/render_slides.py
```

The actual renderer used LibreOffice7.3.7.2 and ran with network=none. All twelve slide PNGs were inspected by Codex; this is separate from student sign-off. Document tools are not web runtime dependencies. PHP8.0 syntax compatibility is a target only: actual PHP8.0 execution and Windows/macOS/professor-host installation remain NOT_RUN.

`python3 tools/package_release.py` needs a reviewed clean Git tree and the isolated evaluation server state; it checks every payload byte plus actual served/captured app identity. `--record-evidence` records one concrete package snapshot for the matrix, after which that evidence can be committed. Final repackaging without the flag writes only dist files, avoiding a self-referential commit loop. The final package's own manifest and external verification identify the authoritative delivered payload commit; matrix T34 retains its actual earlier package snapshot. No final course upload is performed by these commands.
